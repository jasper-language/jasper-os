# issue #7 进度：生产启动与验收编排分离（第一片）

- 日期：2026-10-28 起，2026-11-04 合入
- 范围：第一片——启动阶段图与阶段跟踪器。把 `kmain` 中真正的全局初始化（控制台、平台、定时器、页帧、内核映射、堆、启动期容量、设备、Profile）收敛为 `kernel-core::boot_stage` 中声明的九个阶段，由跟踪器在运行时检查依赖、拒绝重复初始化，任一阶段失败即停止启动；同时把原本藏在演练函数里的初始化（`frame::init`、`map::init`、`heap::init`）提到阶段中，演练只做检查。x86_64 为唯一运行目标；AArch64 只保证能编译。

## 1. 本片做了什么

| 项 | 内容 |
|---|---|
| `boot_stage::Stage` | 封闭枚举（9 个阶段），声明顺序 = 生产执行顺序 = 依赖图的一个拓扑序。 |
| `boot_stage::GRAPH` | 唯一登记点：每个阶段的稳定英文名与直接依赖（位掩码）。新增阶段只改这里与 `Stage`。 |
| `graph_well_formed` | 表位置 = 阶段、名字非空互异、依赖只指向更靠前的阶段（⇒ 无环、无自环）、无越界位；生产表以 `const` 断言，不良构即编译失败。 |
| `closure` | 传递依赖闭包；失败报告据此列出被阻断的阶段。 |
| `boot_stage::Tracker` | `begin` / `complete` / `fail`。检查顺序：已有阶段失败（`halted`）→ 另一阶段在运行（`busy`）→ 重复初始化（`duplicate`）→ 直接依赖未完成（`missing_dependency`，指出最靠前的缺失项）。失败之后任何阶段都不得开始。 |
| 内核 `kmain::stage` | 在跟踪器下执行一个阶段：阶段体返回 `None` 即失败。成功输出 `[JSR-BOOT-STAGE] done stage=<名> done_mask=<掩码>`；被拒输出 `refused stage=<名> reason=<原因>`；失败输出 `failed stage=<名> blocked=<被阻断阶段>`，随后 `[JSR-EXIT] failure boot_stage=<名>` 并退出（退出码与其他功能失败相同，原因由标记区分）。 |
| 初始化与演练拆开 | `mm::demo::run` 改为接收 `frames` 阶段的初始化结果；`run_map` / `run_heap` 不再自行初始化。**行为变化**：以前映射器或堆初始化失败只记为一次演练断言失败、启动继续往下走（随后的容量安装、设备枚举都建立在未初始化的堆上）；现在这两类失败直接停止启动，后续阶段不会开始。 |
| 失败即停 | 定时器等不到 tick（原来直接退出）、没有可用页帧、无物理内存映射、堆首批映射失败、Profile 校验失败，都改为经阶段失败路径停止启动。启动期容量的拒绝仍由 `bootcap::apply` 自行输出结构化原因后退出（标记不变）。 |

### 阶段与依赖

| 阶段 | 直接依赖 | 真实动作 | 失败判据 |
|---|---|---|---|
| `console` | — | 串口、横幅、配置档报告 | 无（串口不可用时无从报告） |
| `platform` | console | 架构早期初始化；断点异常证明异常入口接通 | 异常未返回即无法继续 |
| `timer` | platform | 中断控制器 + 定时器，开中断等到启动 tick 数 | 兜底等待次数用尽（`[JSR-TICK-TIMEOUT]`） |
| `frames` | platform | 按引导内存图建立页帧分配器 | 可用帧为 0 |
| `kernel_map` | frames | 内核映射器 | 引导器未提供物理内存映射 |
| `heap` | frames, kernel_map | 堆首批映射 | 映射或取帧失败 |
| `capacity` | heap | 对象表、实时表、任务表与内核栈按启动期容量安装 | 由 `bootcap::apply` 拒绝并退出 |
| `devices` | kernel_map, heap | PCI 配置空间访问者与只读设备表 | 平台没有 PCI 时设备表为空，不算失败 |
| `profile` | heap | 系统 Profile 校验 | 校验失败项 > 0 |

阶段之间仍穿插验收演练（协作式 / 抢占式调度、64 位计数、机制演练、页帧 / 映射 / 堆演练、PCI 演练等），本片不改变它们的位置与输出。

### 锁序与内存预算

- 阶段全部在引导处理器上串行执行，其他处理器此时尚未启动；跟踪器是 `kmain` 的局部值，不是静态量、不跨核共享，本身不持锁。
- 本片没有改动任何阶段体内部的加锁代码（只是把同一组初始化调用从演练函数移到阶段里），阶段之间不持锁，锁序与改动前相同；阶段内部的锁序由各子系统既有的锁序检查覆盖。
- 内存：跟踪器 16 字节（栈上）；阶段图是只读常量（9 项，每项一个阶段号、一个名字引用、一个 32 位掩码）。阶段机制本身不在堆上分配。

## 4. 与模块 / Profile 装配（issue #6）的边界

- `kmain` 与本模块只负责**全局阶段转移**：哪些全局机制已经就绪、失败时阻止下一阶段。
- 具体服务的依赖与可用性（某服务需要哪些模块、在精简档里是否存在）由模块 / Profile 装配负责；`profile` 阶段只校验声明本身合法，不按服务逐个装配。
- 将来的「用户运行时」阶段只表示「用户态程序可以被装载与运行」，至于运行哪些服务由装配决定。

### 2026-11-04 晚：定时器中断活锁（已修复）

`-icount shift=N` 让虚拟时钟按指令数走，确定性地模拟「处理器相对时钟很慢」。修复前 `shift=8` 稳定卡在第 552 行，`shift=10` 卡在第 64 行，`shift=9` 反而能走过去（和相位有关，不单调）。

**现场**：`shift=8` 下开中断日志 2 秒，引导处理器时钟（向量 0x20）7195 次、本地定时器（向量 0xec）6554 次，**每一次被打断的都是同一条用户指令**。中断返回时下一个已经挂起，被打断的代码一条指令也执行不了。这是活锁，不只是慢。

**开销来源**：一次定时器事务约 2 万条指令量级（按上面的中断频率和 TCG 速度估算，未直接计数）。高精度模式下引导处理器同时有两个定时源；中断返回前的 `current_exiting` 又走一遍调度事务（`lock_state_from` + `refresh_ns_events`）。

**修复**：`kernel_core::timer_progress`。距上一次完整事务结束的窗口不足那次事务开销（开销按 1 tick 封顶）算一次短窗口；连续 2 次短窗口之后，定时器事件只推进时钟并记下欠账，直到窗口够长。推迟的 tick 在下一次完整事务补记运行量；推迟的高精度事件在窗口够长时重新触发一次。

| 结果 | 数字 |
|---|---|
| `scripts/timer-progress-check.sh`（单处理器，shift 5–10，走到第 1200 行） | 修复后 6/6 通过，各 9–13 秒；修复前 shift=8、10 撞 280 秒时限 |
| 正常单处理器启动的推迟次数 | 完整事务 5979 次，推迟 tick 0 次，推迟高精度事件 1 次 |
| 正常 4 处理器完整启动（修复后） | 退出码 37（只有计时项），0 个功能失败，完整事务 13967 次，推迟 12 次 |
| `-smp 2/4` + icount | `shift=8`（4 核）、`shift=9`（2 核）200 秒时限内走到 30 万行以上，没走完。`shift=9`（2 核）有 1 个功能失败：`[JSR-ARB-FAIL] 批处理任务被饿死` |

**边界与未确认的地方**：

- `052742`、`053255` 的现场没有留下寄存器，不能证明它们就是这个活锁。支持的一面：同样停止输出、同样只在高负载下出现；对不上的一面：活锁复现时停在第 552 行或第 64 行，从未复现到 `irqring-driver` 这一行。修复后没有在高负载下重跑这个场景。
- 其他处理器在进入高精度模式之前的本地定时器路径（`on_local_timer`）没有接入保证。加宽限之前的中间版本上，一轮 `-smp 4` + `shift=9` 在 280 秒时限内停在 `[JSR-SMP] clock independent`（第 425 行），推测与此有关，未查证，最终版本未重跑这一档。
- 上面 `shift=9`（2 核）的批处理饿死，判据按时间窗口计算，这个速度下窗口可能不够。未确认是判据问题还是调度问题。
- 事务本身的开销没有降下来，这次只保证了前进。`current_exiting` 走完整调度事务是可以单独优化的。

### 其他处理器的周期定时器接入前进保证（批次全量 `accept-20261105-114916` 通过）

- **现象**：4 处理器 `-icount shift=9` 稳定卡在第 437 行。现场：引导处理器与其他处理器都在调度器锁上排队，其他处理器的本地定时器周期约 14 ms（校准结果被慢时钟拉长），事务开销超过周期。
- **修复**：`on_local_timer` 接入同一套 `timer_progress`。窗口不足时只记欠账；欠账在全局锁内补记，记账内容与正常 tick 相同（抽出 `charge_local_tick`）；有欠账时不走租约快路径。
- **结果**：4 处理器 `shift=9` 不再卡在第 437 行，8 处理器 `shift=9` 也能走过第 1200 行，已加入 `TIMER-PROGRESS` 检查。不带 icount 的完整启动：4 处理器 256 秒、8 处理器 331 秒，退出码都是 37，0 个功能失败；其他处理器推迟次数分别为 0、7。
- **仲裁演练误报**：2 处理器 `shift=9` 的「批处理任务被饿死」不是饿死：切换日志显示 `arb-load` 被多次选中，`batch_started=3`、`batch_ticks=0`，任务还没走到计数循环窗口就结束了。判据拆成功能（窗口内开始运行）与计时（窗口内走到计数循环）。

**仍未解决**：

1. icount 下继续运行到启动后段，还没有一个组合走完：占位任务阶段切换极多（4 处理器 `shift=9` 7 分钟未走完）。
2. 4 处理器 `shift=8` 出现 irqring 失败（`wait_ticks` 上限 1000 tick 内用户程序没走到取消后的等待），2 处理器 `shift=9` 出现 irqstorm 失败（风暴撤销后唤醒延迟不为 0）。两者判据都按时钟计，疑似只是慢，未确认。
