# issue #7 进度：生产启动与验收编排分离（第一片）

- 日期：2026-10-28 起，2026-11-04 合入
- 范围：第一片——启动阶段图与阶段跟踪器。把 `kmain` 中真正的全局初始化（控制台、平台、定时器、页帧、内核映射、堆、启动期容量、设备、Profile）收敛为 `kernel-core::boot_stage` 中声明的九个阶段，由跟踪器在运行时检查依赖、拒绝重复初始化，任一阶段失败即停止启动；同时把原本藏在演练函数里的初始化（`frame::init`、`map::init`、`heap::init`）提到阶段中，演练只做检查。x86_64 为唯一运行目标；AArch64 只保证能编译。

## 1. 本片做了什么

| 项 | 内容 |
|---|---|
| `boot_stage::Stage` | 封闭枚举（9 个阶段），声明顺序 = 生产执行顺序 = 依赖图的一个拓扑序。 |
| `boot_stage::GRAPH` | 唯一登记点：每个阶段的稳定英文名与直接依赖（位掩码）。新增阶段只改这里与 `Stage`。 |
| `graph_well_formed` | 表位置 = 阶段、名字非空互异、依赖只指向更靠前的阶段（⇒ 无环、无自环）、无越界位；生产表以 `const` 断言，不良构即编译失败。 |
| `closure` | 传递依赖闭包；失败报告据此列出被阻断的阶段。 |
| `boot_stage::Tracker` | `begin` / `complete` / `fail`。检查顺序：已有阶段失败（`halted`）→ 另一阶段在运行（`busy`）→ 重复初始化（`duplicate`）→ 直接依赖未完成（`missing_dependency`，指出最靠前的缺失项）。失败之后任何阶段都不得开始。 |
| 内核 `kmain::stage` | 在跟踪器下执行一个阶段：阶段体返回 `None` 即失败。成功输出 `[JSR-BOOT-STAGE] done stage=<名> done_mask=<掩码>`；被拒输出 `refused stage=<名> reason=<原因>`；失败输出 `failed stage=<名> blocked=<被阻断阶段>`，随后 `[JSR-EXIT] failure boot_stage=<名>` 并退出（退出码与其他功能失败相同，原因由标记区分）。 |
| 初始化与演练拆开 | `mm::demo::run` 改为接收 `frames` 阶段的初始化结果；`run_map` / `run_heap` 不再自行初始化。**行为变化**：以前映射器或堆初始化失败只记为一次演练断言失败、启动继续往下走（随后的容量安装、设备枚举都建立在未初始化的堆上）；现在这两类失败直接停止启动，后续阶段不会开始。 |
| 失败即停 | 定时器等不到 tick（原来直接退出）、没有可用页帧、无物理内存映射、堆首批映射失败、Profile 校验失败，都改为经阶段失败路径停止启动。启动期容量的拒绝仍由 `bootcap::apply` 自行输出结构化原因后退出（标记不变）。 |

### 阶段与依赖

| 阶段 | 直接依赖 | 真实动作 | 失败判据 |
|---|---|---|---|
| `console` | — | 串口、横幅、配置档报告 | 无（串口不可用时无从报告） |
| `platform` | console | 架构早期初始化；断点异常证明异常入口接通 | 异常未返回即无法继续 |
| `timer` | platform | 中断控制器 + 定时器，开中断等到启动 tick 数 | 兜底等待次数用尽（`[JSR-TICK-TIMEOUT]`） |
| `frames` | platform | 按引导内存图建立页帧分配器 | 可用帧为 0 |
| `kernel_map` | frames | 内核映射器 | 引导器未提供物理内存映射 |
| `heap` | frames, kernel_map | 堆首批映射 | 映射或取帧失败 |
| `capacity` | heap | 对象表、实时表、任务表与内核栈按启动期容量安装 | 由 `bootcap::apply` 拒绝并退出 |
| `devices` | kernel_map, heap | PCI 配置空间访问者与只读设备表 | 平台没有 PCI 时设备表为空，不算失败 |
| `profile` | heap | 系统 Profile 校验 | 校验失败项 > 0 |

阶段之间仍穿插验收演练（协作式 / 抢占式调度、64 位计数、机制演练、页帧 / 映射 / 堆演练、PCI 演练等），本片不改变它们的位置与输出。

### 锁序与内存预算

- 阶段全部在引导处理器上串行执行，其他处理器此时尚未启动；跟踪器是 `kmain` 的局部值，不是静态量、不跨核共享，本身不持锁。
- 本片没有改动任何阶段体内部的加锁代码（只是把同一组初始化调用从演练函数移到阶段里），阶段之间不持锁，锁序与改动前相同；阶段内部的锁序由各子系统既有的锁序检查覆盖。
- 内存：跟踪器 16 字节（栈上）；阶段图是只读常量（9 项，每项一个阶段号、一个名字引用、一个 32 位掩码）。阶段机制本身不在堆上分配。

## 3. 现有 feature 路径迁移清单（第二片执行）

以下 feature 目前都在 `kmain` 里以 `#[cfg(feature = …)]` 分支「完成前若干阶段 → 运行专项演练 → 退出模拟器」。第二片把它们改为验收登记表中的独立用例，`kmain` 只按登记表选择，不再为每个 feature 加分支；专项用例共用的前置（地址空间 + 启动其他处理器）将成为正式阶段 `space` 与 `smp`。

| feature | 现在的路径 | 迁移去向 |
|---|---|---|
| `user-programs`（默认开启） | 内嵌用户程序，控制十余个演练与失败表行 | 改为「用户运行时」阶段的可用性，由模块 / Profile 装配（issue #6）判定；演练登记时声明依赖该阶段 |
| `rt1-verify` / `rt2-verify` / `rt3-verify` / `rt1-no-realtime` | 专项演练后直接退出 | 登记为专项用例，依赖 `smp` |
| `budget-window-verify` | 同上 | 同上 |
| `krn3-fast-tick-verify` / `krn3-postsplit-verify` / `krn3-p999-verify` | 同上 | 同上（计时类结果继续走「仅计时超界」退出码） |
| `evt1-verify` / `evt2-verify` / `evt2-broadcast-verify` | 同上 | 同上 |
| `s3-nohz-verify` / `shm1-verify` | 同上 | 同上 |
| `fault-inject` | 在默认序列中插入自检 | 故障注入用例，第三片用于阶段失败与回滚的内核内演示 |
| `s2-fuzz` / `krn1-soak` | 默认序列末尾追加 | 登记为独立长跑用例 |
| `bm1-vm` / `bm1-hang` / `krn2-observe` | 不在 `kmain` 分支内 | 不迁移（平台设备配置与观测计数，不属于验收编排） |

## 4. 与模块 / Profile 装配（issue #6）的边界

- `kmain` 与本模块只负责**全局阶段转移**：哪些全局机制已经就绪、失败时阻止下一阶段。
- 具体服务的依赖与可用性（某服务需要哪些模块、在精简档里是否存在）由模块 / Profile 装配负责；`profile` 阶段只校验声明本身合法，不按服务逐个装配。
- 将来的「用户运行时」阶段只表示「用户态程序可以被装载与运行」，至于运行哪些服务由装配决定。

### 此前几次全量失败的原因

本片变基后有四次全量未通过，都是撞时限，没有功能断言失败；日志截断造成的 FAIL 行不算独立失败。逐次如下，「未查清」的部分没有下结论：

| 全量 | 现象 | 现场说明了什么 |
|---|---|---|
| `accept-20261104-090048`（nice 5） | 单处理器串口全空，撞 600 秒 | 不是内核问题：栈上解码为引导第二阶段 `fail('z')`，即固件 `int 13h` 读盘报错，panic 只写 VGA 后 `hlt`，客户机没进内核。vCPU 累计约 36 秒 CPU，与 SeaBIOS 的 32 秒 IDE 超时相符（推断）。**读盘报错的根因未查清**：同期 O_DIRECT 读探针最大约 306 ms，不支持「I/O 被饿死」的猜测，但当时没有卡顿记录。 |
| `accept-20261104-102102`（nice 5） | S-2 撞 2400 秒 | 只是慢：8 个 vCPU 都在运行，票据锁计数持续增长。同一轮卡顿探针记到写 + fsync 最长 8.6 秒，负载最高约 32。 |
| 同上 | q35 撞 600 秒 | 只是慢：vCPU0 5 秒用约 4.5 秒 CPU，寄存器在变，日志到 34950 行（完整约 38000 行）。 |
| `accept-20261104-053255`、`072753`（nice 19） | 单处理器 / q35 / S-2 撞时限 | **未查清**。当时的 q35 现场两次采样寄存器相同且 `IRR` 挂着 236，曾被当作 vCPU 没在执行的证据；但新现场里睡眠中的 vCPU 同样挂着 236，这个判据不成立。这两次是否也只是慢，没有线程用量数据，无法确认。 |

相应改动：撞时限且串口没有第四阶段引导输出时重跑一次（第二次即最终结果）；S-2 默认时限改为 4200 秒；现场工具增加线程阻塞点与 VGA 文本屏，S-2 也接入；全量记录文件系统卡顿。未对比 main 基线（三次通过均在此前，负载不同），所以「nice 19 下未过与本片无关」没有直接证据。

## 6. 剩余切片

1. **第二片：生产模式与验收登记表。** 增加 `space`、`smp`、用户运行时阶段；验收用例改为静态登记表（名称、依赖阶段、是否计时类、失败汇总项），按构建期清单选择；第 3 节的 feature 分支全部迁移；生产模式在阶段完成后进入空闲等待（不退出模拟器），验收模式跑完登记用例后按失败表退出。
2. **第三片：失败、回滚与重复初始化的内核内证明。** 为可回滚阶段声明回滚动作（例如容量安装失败时释放已安装的表），故障注入用例在真实内核中让指定阶段失败，验证被阻断的阶段确实未开始、已占资源回到基线、重复初始化被拒。
